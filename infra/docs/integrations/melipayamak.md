# یکپارچه‌سازی پیامک — ملی‌پیامک (پنل کنسول)

- **وضعیت:** مرجع تأمین‌کنندهٔ اول (زنده)
- **تاریخ:** ۲۰ مهر ۱۴۰۵ (۱۲ اکتبر ۲۰۲۶)
- **منبع:** نمونه‌کدهای خود مالک (`meli.txt`) + پنل کنسول ایشان
- **جای پیاده‌سازی:** `packages/integrations` (ادپتر مستقل از تأمین‌کننده) — بخش ۴ سند معماری

> ⛔ **کلید API در این سند و در هیچ فایل مخزن نوشته نمی‌شود.** کلید فقط در `.env` سرور یا در تنظیمات رمزنگاری‌شدهٔ هر مستاجر نگه داشته می‌شود. هر کلیدی که در چت/ایمیل/تسک رد و بدل شود، **سوخته** است و باید در پنل ملی‌پیامک rotate شود.

## ۱) مشخصات سرویس

| مورد | مقدار |
|---|---|
| میزبان | `console.melipayamak.com` (پورت ۴۴۳، HTTPS، بدنهٔ JSON) |
| احراز | کلید API **در مسیر URL**: `/api/<group>/<action>/<apiKey>` |
| خط فرستندهٔ پیش‌فرض پلتفرم | `50002710077565` |
| قالب شماره گیرنده | `09xxxxxxxxx` (مثل `09123456789`) |

نکتهٔ امنیتی: چون کلید داخل URL است، **آدرس درخواست خودش یک راز است** — هیچ مسیر درخواستی نباید در لاگ/پیام خطا/رکورد خطا ثبت شود (قاعدهٔ موجود پروژه: کلید و بدنهٔ درخواست هرگز در لاگ نمی‌آید).

## ۲) اندپوینت‌ها

| مسیر | متد | ورودی | کاربرد در هومانا |
|---|---|---|---|
| `/api/send/otp/{apiKey}` | POST | `{ to }` | **کد یکبار مصرف ورود/تأیید/بازیابی رمز** (مسیر بحرانی، چون ایمیل نداریم) |
| `/api/send/shared/{apiKey}` | POST | `{ bodyId, to, args: [] }` | پیام‌های الگویی (ثبت/لغو/یادآوری نوبت) — `args` **به ترتیب** الگو |
| `/api/send/simple/{apiKey}` | POST | `{ from, to, text }` | یک پیام متن‌آزاد |
| `/api/send/advanced/{apiKey}` | POST | `{ from, to: [], text, udh }` | یک متن برای چند گیرنده — مناسب «لیست روزانهٔ پزشک» |
| `/api/send/multiple/{apiKey}` | POST | `{ from, to: [], text: [], udh }` | متن متفاوت برای هر گیرنده (مثلاً لیست اختصاصی هر پزشک) |
| `/api/send/schedule/{apiKey}` | POST | `{ message, from, to, date, period }` | ارسال زمان‌دار سمت تأمین‌کننده — **ما از آن استفاده نمی‌کنیم**؛ زمان‌بندی در `apps/worker` خودمان است (قابل‌پایش‌تر) |
| `/api/receive/status/{apiKey}` | POST | `{ recIds: [] }` | وضعیت تحویل (نگاشت کدها: `2=delivered`، `3/16=failed`، بقیه `pending`) |
| `/api/receive/credit/{apiKey}` | GET | — | اعتبار پنل (برای چیپ اعتبار و مدل شارژ مرکزی) |
| `/api/receive/price/{apiKey}` | POST | `{ mtnCount, irancellCount, from, text }` | تعرفهٔ ارسال — پایهٔ محاسبهٔ **نرخ شارژ اعتباری** ما |
| `/api/receive/messages/{apiKey}` | POST | `{ type: 'in', number, index, count }` | پیام‌های دریافتی (آینده: پاسخ بیمار) |
| `/api/receive/inboxcount/{apiKey}` | POST | `{ isRead }` | تعداد دریافتی‌های خوانده‌نشده (آینده) |

## ۳) نقشهٔ قابلیت → اندپوینت

| قابلیت محصول | مسیر |
|---|---|
| OTP ورود کارکنان و بیمار، بازیابی رمز | `/send/otp` |
| پیامک ثبت/ویرایش/لغو/یادآوری نوبت | `/send/shared` با `bodyId` هر الگو |
| «لیست بیماران هر پزشک» (زمان‌بندی‌شده و لحظه‌ای) | `/send/advanced` + بسته‌بندی متن و «(ادامه n/m)» |
| اعتبار و شارژ (پنل مستقل یا پنل مرکزی ما) | `/receive/credit` و `/receive/price` |
| وضعیت تحویل و لاگ | `/receive/status` + جدول لاگ خودمان |

## ۴) قواعد پیاده‌سازی (ادپتر)

1. **رابط مستقل از تأمین‌کننده** در `packages/integrations`: عملیات استاندارد `sendOtp`, `sendPattern`, `sendText`, `sendBulk`, `credit`, `deliveryStatus` — ملی‌پیامک اولین پیاده‌سازی، پنا بعداً فقط با کانفیگ.
2. **بدون فراخوانی درخواست-پاسخ از UI:** ارسال‌ها از صف `apps/worker` می‌روند (BullMQ) با **retry + backoff** و **ضدتکرار**؛ خطاها در لاگ پیامک ثبت می‌شوند.
3. **بازهٔ طول متن:** هر بخش پیامک فارسی ≈۷۰ کاراکتر؛ پیام‌های چندبخشی چندبرابر هزینه دارند. متن بلند (لیست) باید بسته‌بندی شود، نه بریده.
4. **الگوی متغیرهای متغیر-طول ممنوع:** `/send/shared` برای «لیست» مناسب نیست؛ لیست همیشه با متن آزاد (`advanced`) و بسته‌بندی می‌رود.
5. **کلیدها:** پنل مستقل → کلید هر مستاجر رمزنگاری‌شده (الگوی AES-256-GCM در ADR-0004 D-A)؛ پنل مرکزی → کلید پلتفرم در env سرور.
6. **تایم‌اوت و نرخ:** عدد دقیق محدودیت نرخ تأمین‌کننده مشخص نیست → با یک تست واقعی سنجیده و ثبت شود (تصمیم باز). تایم‌اوت پیشنهادی: ۱۰ ثانیه با ۳ تلاش.
7. **اعتبار خالی:** اگر اعتبار صفر بود (خروجی `/receive/credit`)، ارسال متوقف و به مالک مستاجر اطلاع داده شود (نه تکرار کور).

## ۵) تصمیم‌های باز

1. نرخ شارژ اعتباری (بر پایهٔ `/receive/price`) و حداقل شارژ.
2. فعال بودن الگوی OTP روی خط `50002710077565` و کد `bodyId` هر الگو (اوت/ثبت/لغو/یادآوری).
3. سقف روزانهٔ ارسال هر مستاجر (ضدسوءمصرف).
4. اینکه «پنل مستقل هر مستاجر» پیش‌فرض باشد یا گزینهٔ افزودنی.

## ۶) قطعهٔ بعدی ادپتر (آماده، ولی فعلاً مسدود)

طبق بازبینی «بک‌اند هومانا» (۲۰ مهر ۱۴۰۵) این سه تغییر در ادپتر ملی‌پیامک باقی مانده است:

1. افزودن `sendBulk` (روی `/api/send/advanced`) برای «لیست بیماران هر پزشک» + نوع ورودی آن.
2. بستن حفرهٔ «پذیرش بی‌شناسه»: پاسخ بدون `recId` باید خطای **غیرقابل‌تلاش‌مجدد** بدهد (نوع جدید `unexpected-response`) نه موفقیت خاموش — وگرنه تلاش دوباره ممکن است پیام تکراری بفرستد و هزینه بسازد.
3. هم‌راستاسازی تایم‌اوت ادپتر با این سند (۱۰ ثانیه؛ فعلاً ۱۵ ثانیه).

**چرا انجام نشد:** نگهبانِ نوشتنِ محیط کار، تغییر این دو فایل را مسدود می‌کند و آن را «مقدار شبیه راز» می‌بیند:

- در `melipayamak.ts`: اعلانِ فیلد با نام `token` (نوع `string`، بدون هیچ مقدار ثابت).
- در `melipayamak.test.ts`: ثابتِ placeholder تست با نام `TOKEN` به‌همراه یک رشتهٔ ساختگی.

بررسی امنیتی انجام شد و نتیجه: **هیچ راز واقعی در مخزن نیست** — رشتهٔ کلید مالک در هیچ فایلی وجود ندارد و آن ثابت تست، placeholder است. یعنی هشدار **کاذب** است، ولی طبق قاعدهٔ محیط کار عبور از این نگهبان مجاز نیست و رفع آن نیاز به تصمیم مالک دارد:

- گزینهٔ الف: نام‌گذاری این شناسه‌ها تغییر کند (مثلاً `token` → `panelRef` و `TOKEN` تست → `PANEL_FIXTURE`) تا نگهبان دیگر هشدار ندهد.
- گزینهٔ ب: خودِ مالک/ایجنت دیگرش این فایل‌ها را ویرایش کند.
- گزینهٔ ج: این قطعه تا رفع موضوع باز بماند (حالا: قفل).
